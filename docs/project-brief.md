# AI Roleplay Chat - Project Brief

## Overview

ChatGPTを利用した、対話型のiPhoneアプリを開発する。

通常のAIアシスタントではなく、AIが特定の人物・役割を演じ、ユーザーがその相手と会話する「ロールプレイ型チャットアプリ」を想定している。

GitHub repository:

`git@github.com:hibiki-tsuboi/ai-roleplay-chat.git`

ホーム画面の表示名は「AIロープレ」。正式なアプリ名は未定。

`ai-roleplay-chat` は開発用の仮名称。

---

## Product Concept

AIが以下のような役割を演じる。

- 部下
- 上司
- メンター
- 後輩
- 顧客・取引先

最初のMVPでは「AI部下との会話」を中心に検討する。

次の4シナリオを実装済みで、会話を始める前に選択する。

- 提出が遅れている部下（田中）
- ミスを報告してきた部下（佐藤）
- やる気が下がっている部下（鈴木）
- 態度に問題がある部下（山本）

ユーザーは上司としてAI部下と会話する。人物設定はバックエンドが持ち、アプリはシナリオIDだけを送る。

部下以外の役（上司・メンター・顧客など）はユーザーの立場が変わるため、採点の4項目をそのまま使えない。役ごとの採点基準とスコアの意味づけを決めてから着手する。

新しい練習は5往復（ユーザーの発言と部下の返答で1往復）で終了し、「今回の上司度」を100点満点で表示する。

- 事情を聞く・相手への配慮・指示の明確さ・次の行動の合意を各25点で評価する。
- 良かった点、改善点、具体的な言い換え例を1つずつ示す。
- 人格や管理職としての能力を断定せず、今回の会話を振り返るための目安とする。
- 結果を会話とともに端末に保存し、「もう一度挑戦」で同じシナリオ・AI の新しい練習を始める。
- 過去の自由形式の会話は保持し、5往復の練習へ途中変換しない。

## Architecture

Monorepoで管理する。

```text
ai-roleplay-chat/
├── ios/
├── backend/
├── docs/
├── AGENTS.md
└── README.md
```

### iOS

- Swift
- SwiftUI
- SwiftData

チャット履歴は、MVPでは基本的にiPhone端末内へ保存する。

会話開始時にOpenAI / Geminiを選択し、その会話の接続先を履歴とともに保存する。会話を再開するときも同じAIを使う。モデル名とAPI Keyはバックエンドで管理する。

### Backend

Cloudflare Workersを利用する。

役割は主にAI APIへの安全なプロキシ。ローカルとCloudflareの開発環境でOpenAI / Geminiを選択できる。

```text
iPhone App
    ↓ HTTPS
Cloudflare Workers
    ↓
OpenAI API / Gemini API
```

OpenAI・GeminiのAPI KeyをiOSアプリ内には保存しない。

Cloudflare Workers側のSecretとして管理する。ローカルではGit管理外の`backend/.dev.vars`を使う。

MVPではバックエンド側に大規模なDBやユーザー管理を持たせない方針。

## OpenAI

OpenAI APIを利用してAIとの対話を実現する。

AIには単なるアシスタントとして回答させるのではなく、

「特定の性格・背景・役割を持つ人物」

として会話させる。

例:

```text
あなたはユーザーの部下です。

性格:
- 真面目
- やや自信がない
- 報告が遅れがち

状況:
昨日までに提出する予定だった資料がまだ完成していません。

ユーザーはあなたの上司です。
部下として自然に会話してください。
```

会話用プロンプトは往復数に応じて最後の返答を締めくくるよう指示する。採点は別のコーチ用プロンプトで5往復全体を評価し、検証済みの構造化データとして返す。

## MVP

まずは非常に小さく作る。

想定する最低限の機能:

1. シナリオを1つ選択
2. AI部下とのチャット画面を表示
3. ユーザーがメッセージを送信
4. Cloudflare Workers経由で選択したOpenAI / Gemini APIへ送信
5. AI部下の返答を表示
6. 会話履歴をSwiftDataへ保存
7. 5往復終了後に同じAIで採点し、上司度とフィードバックを表示・保存
8. 履歴から結果を振り返り、新しい練習へ再挑戦

認証・クラウド同期・サブスクリプションなどは後回しにする。

## Development Policy

まず動くMVPを作る。

過度な抽象化や将来を見越した複雑な設計は避ける。

以下を優先する。

1. シンプル
2. 読みやすい
3. 小さく実装
4. 動作確認しながら段階的に拡張

正式名称・デザイン・課金モデルなどは、MVP完成後に検討する。
